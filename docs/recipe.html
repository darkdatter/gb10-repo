Rig: ASUS DGX Spark · GB10 · 128 GB unified · Ubuntu 24.04, kernel 6.17-nvidia · driver 580.173.02 / CUDA 13.0 · Docker 29.2.1 · nvidia-container-toolkit 1.20 (CDI)

Start here if you read nothing else

NVFP4 beats FP8, and SGLang beats vLLM, on this hardware. The widely-shared “Qwen3.8-27B FP8 on vLLM at ~32 tok/s” recipe is roughly half the speed of this one. NVIDIA’s own forum benchmarks put NVFP4 29–34% ahead of FP8 on vLLM; moving to SGLang with DFlash2 speculative decoding roughly doubles it again.

01

Prove GPU passthrough first

Five minutes here saves an hour of misdiagnosis later. DGX OS ships CDI rather than a registered Docker runtime, so docker info shows only runc — that is normal and --gpus all still works.

docker run --rm --gpus all nvidia/cuda:13.0.1-base-ubuntu24.04 nvidia-smi -L
# expect: GPU 0: NVIDIA GB10 (UUID: GPU-...)

If that fails, try --device nvidia.com/gpu=all. Only if both fail:

sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker
02

Build the DFlash2 image

This is the step most people trip on.

Trap

lmsysorg/sglang:qwen38-27b-dflash2 is not on Docker Hub. SparkStation’s models.yaml references it, but no released SGLang tag ships DFlash2 — you build it yourself. The base :qwen38-27b tag does exist.

git clone --depth 1 https://github.com/MiaAI-Lab/Qwen3.8-27B-SGLang-DGX-Spark.git
cd Qwen3.8-27B-SGLang-DGX-Spark
./patch/build-dflash2-image.sh --full   # pulls 39GB base, then overlays

--full clones SGLang at a pinned commit and applies an NVFP4 head patch. That patch matters: the earlier approach dequantized the whole NVFP4 lm_head at draft-graph capture and hard-rebooted the machine. Use --minimal for a checksum-verified 5-file overlay that needs no network.

03

Pre-download the weights

Do this on the host, not from inside the container — it parallelizes with the image build and sidesteps the launcher’s auth gap (see traps).

python3 -m venv ~/spark/venv
~/spark/venv/bin/pip install -U huggingface_hub
~/spark/venv/bin/hf auth login          # optional: rate limits only

~/spark/venv/bin/hf download RadixArk/Qwen3.8-27B-NVFP4
~/spark/venv/bin/hf download z-lab/Qwen3.8-27B-DFlash2 \
  --revision 50307d4c4cde6860d4eee73e2547cd786fe8e8a4
Trap

Let these land in the real ~/.cache/huggingface. If you symlink hub/ or xet/ inside that directory, the container mounts the folder and sees links pointing at host-only paths — it decides nothing is cached, re-downloads, and dies with OSError: I/O error: File exists (os error 17).

Symlink the other direction if you need to: point a repo path at ~/.cache/huggingface. Docker resolves -v host-side, so that is safe.

04

Run it standalone and benchmark

Get a number before adding a control plane. If something breaks later, you’ll know whether it was the model or the orchestration.

cd Qwen3.8-27B-SGLang-DGX-Spark   # REQUIRED: start.sh uses WORK_DIR="$(pwd)"
cp .env.sample .env
DF_EXTRA="--mem-fraction-static 0.85" ./start-dflash.sh

Serves on :8888 as qwen3.8-27b-sglang, OpenAI- and Anthropic-compatible. First boot ≈3 minutes.

Memory ceiling

The script defaults NVFP4 to 0.90; the generic start.sh uses 0.95. Both the toolkit and SparkStation record machines unrecoverably wedged during weight load at high fractions — GB10 unified memory starves the OS. I used 0.85 on first boot. If you can’t physically reach the box to power-cycle it, do the same.

05

Put SparkStation in front

Gives you one OpenAI endpoint, lifecycle management, auto-suspend, and thermal policy.

curl -LsSf https://astral.sh/uv/install.sh | sh
git clone --depth 1 https://github.com/kshetrajna12/sparkstation.git
cd sparkstation && uv sync
cp .env.example .env    # TOTAL_UNIFIED_MEMORY_GB=128, MEMORY_HARD_LIMIT_GB=110

Then one required edit in models.yaml — the qwen3.8-sglang entry ships pinned to a second machine:

# models.yaml, under qwen3.8-sglang:
-   host: worker1
+   host: primary
uv run sparkstation start -d --profile generic
uv run sparkstation status

Gateway on :8000, supervisor on :9001. The model container is bridge-networked, so its internal :8000 maps to host :8001 — no collision with the gateway despite both reporting 8000. Gateway overhead measured at zero (62.3 vs 62.5 tok/s direct).

06

Unlock concurrency — the biggest win

The shipped config caps you at 4 concurrent requests and leaves most of the box idle. Three flags are co-limiting; raising only the obvious one measures nothing.

# models.yaml → qwen3.8-sglang → extra_args → sglang_flags
- "--max-running-requests"      → "16"
- "--max-mamba-cache-size"      → "80"   # 16 requests x 5 slots
- "--cuda-graph-max-bs-decode"  → "16"   # else batches >4 fall back to eager
The 5-slot rule

Qwen3.8 is a hybrid (Gated DeltaNet) model, so concurrency is bought with mamba state, not KV cache. Each request needs 5 GDN state slots — 4 plus one for DFlash2’s verify step. SGLang silently clamps max_running_requests = pool / 5 and tells you in the log: capped to 12 by the mamba state cache. Size the pool at 5× your target.

It isn’t free: an 80-slot pool allocates 15.6 GB and drops free GPU memory from 38 → 21 GB.

Aggregate tok/s. 16 streams is a true optimum, not a plateau: TTFT p50 and max are identical there (0.68 s — zero queueing, because streams equal the cap), while 24 and 32 are both slower in aggregate and blow latency out past 10 s.

The cost is ~5% single-stream — 63.1 → 60.0 tok/s, from the larger decode CUDA-graph set. Worth it for multi-agent work; revert if this is a single-user box.

Don’t misread thinking mode

My first thinking-on run scored a worse 90.9% — and it was entirely an artifact: 14 of its 15 failures had finish_reason == "length". The model reasoned past a 4,096-token budget and never emitted code.

With a 16K budget it reaches 97.0%. Of the 5 remaining failures, only one is a genuine wrong answer — the other four burned the full 16K without terminating. That is the overthinking pathology SparkStation’s config explicitly guards against by pinning reasoning effort to medium. Always pair a token cap with a finish_reason check, or silent truncation reads as a quality regression.

Practical default: thinking off for well-specified functions — 93.9% at a fifth of the tokens and 6× the speed. Switch it on for hard cases.

Every trap, in one list

The DFlash2 image doesn’t exist upstream

SparkStation’s models.yaml names lmsysorg/sglang:qwen38-27b-dflash2, but no released SGLang tag ships DFlash2. Build it with patch/build-dflash2-image.sh before starting anything.

HF cache symlinks inside the container mount break everything

The container mounts ~/.cache/huggingface. Symlinks within it point at host paths that don’t exist inside the container, so it re-downloads and fails on xet with File exists (os error 17). Keep real directories there.

host: worker1 assumes a second Spark

The shipped qwen3.8-sglang entry is pinned to a worker node. On a single Spark set host: primary. The default generic profile uses the base spec, so nothing overrides it back.

start.sh uses WORK_DIR="$(pwd)"

Not the script directory. Run it from inside the repo or your HF cache and Triton cache land wherever you happened to be standing.

5 mamba slots per request, not 4

DFlash2’s verify step needs an extra slot. max_running_requests is silently clamped to pool / 5. The log says so explicitly — read it after a config change.

uv installs cli.py into site-packages

Editing cli.py in the repo does nothing — the console script resolves import cli from .venv/bin, not your cwd. Copy the file to .venv/lib/python3.12/site-packages/cli.py too. Related: in the installed copy __file__ is site-packages, so use PROJECT_ROOT to find .env / models.yaml.

Gateway reports “not healthy” while working fine

_gateway_healthy() hardcodes Bearer dummy-key, so any custom LITELLM_MASTER_KEY returns HTTP 400 and status false-negatives. CLI-only — the supervisor doesn’t use it — but it costs a spurious warning and a 30 s stall on every start. Patch it to read the configured key, or leave the default key alone.

Only the FLUX launcher forwards HF_TOKEN

sglang_launcher.py and vllm_launcher.py don’t pass it into the container, so a gated model can’t authenticate its own download. Pre-pull on the host with hf download (which is the better workflow anyway).

Never docker rm -f a managed container

The supervisor’s state goes stale and both stop (HTTP 500) and start (HTTP 409) then fail. sparkstation stop && sparkstation start reconciles it.

Greedy decoding is not bitwise deterministic

At temperature 0, repeated runs still flip 2–3 HumanEval problems, because dynamic batching plus speculative decoding changes reduction order. Don’t read a sub-2% delta as a regression.

Thinking is on by default

A small max_tokens returns empty content with everything in reasoning_content. Disable per request with chat_template_kwargs: {"enable_thinking": false}.

Sanity check

curl -s http://127.0.0.1:8000/v1/chat/completions \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"default",
       "messages":[{"role":"user","content":"Say exactly: it works"}],
       "max_tokens":200,
       "chat_template_kwargs":{"enable_thinking":false}}'
Measured on a single ASUS DGX Spark, August 2026. Throughput figures are LRUCache-style code generation at temperature 0, counting completion_tokens over wall time — DFlash2 emits ~3.75 tokens per SSE event, so counting stream events instead will mislead you. Your mileage will vary with prompt shape.
